# SPEC：正式待办 MVP

本 SPEC 依据用户已批准的 MVP 任务及 2026-10-30 的补充约束。第 0、1 阶段已确认。当前按用户最新审核服务需求推进第 2 阶段；因新增重绑定与失效出口，拆为各不超过一天的 2A、2B。本轮仅实现 2A，完成后提交并等待确认。

## 全局边界

- 独立正式任务模块；不修改决定流程、ActionRecord、关系旁库、Ask / legacy-ask 或现有静态文件。
- 同一任务由人选择，不自动推断或合并。后续页面只增加新路由和新静态资源。
- 证据是有序列表，每段保存来源标识与版本、发言或行位置、原文和哈希；支持一条候选包含多个来源段、多个版本。
- 核心使用统一候选输入契约，不 import TaskObservation，不依赖其内部字段。旧 TaskObservation 适配在第 2 阶段接入；后续 v2 可实现独立适配。
- 不写 README。过程资料只在 docs/task-mvp 临时保留，最后阶段浓缩至 PR 描述并按用户授权删除该目录。
- 每阶段单独提交并停止等待确认。PR #30 合并后，将 origin/master 合并到当前分支，确认原有 5 个 cp936 失败消失；不在本功能分支自行修改其修复代码。

## 第 1 阶段范围

新增 src/linkloom/tasks/__init__.py、models.py、store.py 以及对应单元测试。review.py 服务、旧候选适配、HTTP 和页面不在本阶段实现。

模型包含 task 当前快照（状态 open / in_progress / blocked / done / cancelled，新建默认 open）、只追加 task_event 和唯一 observation_id 的 task_observation_link。忽略候选时 task_id 为空。为工作区隔离、顺序和审核指纹，可增加内部约束字段；不改变旧表、旧 user_version 或旧行为。

统一输入保存工作区、候选标识及版本、标题、owner、deadline / deadline_text、会议原文时间和多段证据，提供稳定候选指纹。证据哈希验证逐字原文，允许发言定位或完整行范围；不推断缺失时间和年份。

## Store 合同

- 创建和字段变更、事件及候选处理记录在同一个 SQLite 事务中提交；异常必须整体回滚。
- 核心不判断是否为同一任务；merge 仅对调用方明确选择的 title / owner / deadline 应用实际变化。deadline 与 deadline_text 作为一个字段对更新，生成一条 deadline_changed。
- 提供手动状态更新的存储操作。created 事件保存完整初始快照；事件使用稳定追加顺序，重放后包括字段、id、workspace、时间的快照与当前 task 相同。
- 所有读写显式绑定 workspace；复合外键阻止跨工作区事件或链接。重复处理同一候选必须拒绝，不能创建第二个任务或部分事件。
- reviewer / actor 和 reason 非空；保存候选指纹及来源证据用于后续审核读回。来源版本汇总字段可空，证据列表各段必须保持自己的版本，不能只保留第一段。
- 审核产生的创建 / 字段变更事件必须有证据列表；纯手动状态变更可无来源证据与会议时间。
- 只追加事件由数据库约束防止 UPDATE / DELETE。迁移仅增加任务相关表和约束，保留无关表、数据和原有数据库版本。

## 第 2A 阶段：审核服务（用户最新要求）

输入是统一候选契约；只实现旧 TaskObservation 适配器，不接新 v2 抽取器、HTTP、页面或模型。新服务不开放 merge，也不实现自动任务匹配或跨会议合并。2B 留待确认后实现同源新版人工重绑定及“已失效”出口。

### 输入、输出与文件边界

- 新增 tasks/review.py、legacy_adapter.py、review_storage.py 及对应单元测试；models.py 仅扩展统一候选输入所需的可空原始标题及原始候选指纹，不放宽正式 Task.title 的非空要求。必要的数据契约可放独立模块；不修改旧决定、Ask、ActionRecord、关系旁库或抽取器。
- 原候选快照、候选指纹与人工字段 patch 分开保存。字段 patch 仅允许 title、owner、deadline（含 deadline_text），区分未提供与显式清空；日期不猜年份。
- 查询输出包含正式任务字段、独立 review_status（approved / needs_review）、审核版本令牌、逐字段 source/human 来源、审核历史及事件。人工来源有 reviewer、reason、时间及所依据的原始候选指纹；证据以有序列表保存。
- 原 description 为空时统一输入保留 title=null；确认必须人工补充非空标题并标为 human，禁止把 raw_text 冒充抽取标题。

### 审核和一致性

1. confirm：人工确认当前候选，可附字段修改。仅一次审核审计事件，保存原始字段、最终字段、显式人工字段集合、原始候选快照与指纹、reviewer / reason / 操作时间；created 任务事件保存最终初始快照。未改字段来源为 source，人工 patch 字段为 human。
2. reject：记录候选首次消费链接及一次审核事件，不创建或修改任务。
3. edit_fields：确认后人工修改本任务的 title / owner / deadline；每个实际值变化追加对应 task_event；一次操作记一次审核事件。人工新值的证据只作背景引用，不能宣称新值被原文支持；会议时间为空，原证据仍保留原会议时间。无实际值变化也保留明确提交的审核审计。
4. reviewer 和 reason 非空；操作必须带预览的候选指纹；任务修改还带预览的审核版本令牌，防止并发覆盖。重复初次确认 / 拒绝拒绝；首次 link 的 observation_id 唯一约束保留，不伪造 ID 或删除链接。
5. 查询重新核对当前候选、来源版本及原文绑定；失配后追加失效审核事件并锁存 needs_review，保留 task 业务 status、快照与全部历史，不自动回滚。A→B→A 不能自动恢复旧确认；来源失效后不允许用旧确认继续编辑。相同候选仍当前时可显式重新确认；新 ID 重绑定不在 2A。
6. 新增独立审核元数据和只追加审核表，不改变 task_schema_metadata v1 及原有表字段。为覆盖未查询间隙的版本往返，可用任务专有来源变更日志/触发器观察 ll_source 版本和 active 切换，仅追加任务日志；不改写旧表数据或旧代码路径。
7. 审核 schema 探测与创建在 BEGIN IMMEDIATE 内；在同一数据库同一事务内重新读取候选和来源、核对指纹与任务令牌、验证原文，再一起提交快照、任务事件、链接和审核审计。异常整体回滚；所有读取和写入显式绑定 workspace。
8. 旧适配器完整验证候选序列化指纹、工作区、来源当前性和 TaskObservation.verify(原始版本)；完整旧候选内容（忽略导入时间重复）与冲突上下文绑定进审核指纹。不能任意挑抽取冲突的第一条；只能按精确预览指纹定位唯一变体。原文会议时间使用 event_time。

### 2A 验收与验证

- 原始空标题的人工补充、可空负责人、期限文本及显式清空；非法输入不产生部分写入。
- 老适配器真实候选往返及版本原文校验；统一核心不依赖 TaskObservation，通用多段证据保持列表顺序。
- 旧指纹、重复审核、并发审核、并发任务编辑、错误 workspace、来源变更 / 撤销和 A→B→A；needs_review 锁存且任务业务状态、历史和快照不回滚。
- 事件重放与快照一致；注入事件、链接或审核写入失败后全部回滚；独立审核 schema 重开 / 初始化兼容原 task schema v1 和原测试。

### 2B 的已确认范围（本轮不实现）

仅人工指定同一来源文档较新版本的新候选，验证新版原文，逐字段展示差异并由审核人选最终值；拒绝跨文档 / 跨会议，不能自动匹配或覆盖。重绑定追加一次审核事件（旧 / 新指纹、reviewer、reason、时间），保留旧证据。新版该任务已不存在时允许人工标“已失效”并保留历史。版本 ID 为哈希；新版顺序需由真实来源版本目录证明，不按哈希、会议时间或导入时间猜测。没有同会证明时拒绝重绑定。

2A 重确认语义澄清：同一候选仍当前时，显式重新确认必须携带 expected_review_revision，复用原 task_id，不重复创建或追加第二个 created。保留现有 task 快照、业务状态和未提供 patch 字段的来源；只有显式 patch 的实际值变化才追加字段事件。一次重确认产生一次审核审计，恢复 approved，不把已有人工值自动替换回候选值。确认依据要对每个证据来源保存事务内捕获的 source epoch；失效只幂等追加一次并锁存。
